# #39 — Surface possible duplicate workouts during sync

**Closed:** 2026-05-31
**Branch:** `claude/pedantic-gauss-578a49`

## What was asked

Tom occasionally sees outlier activities he can't explain — a real-world session that exists twice in HealthKit because a second app (e.g. Strava alongside Peloton / Apple Watch) wrote its own copy. He can't auto-delete them (HealthKit only lets an app modify samples it authored, #12 — and these are *other* apps' samples), so the ask was narrow: during a sync, **detect and display** likely duplicates (same time, duration, distance…) so he can find and delete the extra manually in the Health app.

## The governing constraint (why this is display-only)

This is the inverse of #37. #37's duplicates were **app-authored** — created by our own `.noMatch` path — so we could and did delete them. #39's duplicates originate from apps we don't own, and the #12 ownership rule blocks deletion outright. So the whole feature is read-only: cluster, surface, point Tom at what to remove himself. No deletion API is even attempted.

## Design (decided up front with Tom)

Two product decisions were put to Tom before coding:

1. **Scan scope → ride-along with each sync.** Reuse the HealthKit workouts already fetched per activity (`workouts(in: start...end)`, proxies filtered) — zero extra queries. Tradeoff he accepted: only flags duplicates within the windows of activities actually synced (recent window), so pre-existing historical outliers won't surface unless re-synced. A one-time wide-scan button (like #37's cleanup, but read-only) was named as a possible follow-up and left out of scope.
2. **Match rule → same type + start ±60s + duration ±60s.** Same tolerances `Matching` already uses. Distance is **shown for corroboration but is not a match key** — so an indoor ride lacking native distance still pairs with its twin. Rejected alternatives: requiring distance to match (would hide real dupes where one source has no distance), and cross-source-only filtering (would miss two-from-one-source cases).

## How it works

- **`DuplicateDetection.swift`** — a pure clusterer over plain structs (`WorkoutForDuplicateCheck`), mirroring the `Matching` / `DistanceEnrichment` pure-gate pattern so the logic is unit-testable without `HKWorkout`. Union-find groups workouts that pairwise share type and fall within ±60s on start and duration; singletons dropped. "Within tolerance" isn't transitive, but at the scale here (a handful of workouts in one activity's ±5min window) any reasonable grouping is equivalent. `DuplicateCluster.id` is the sorted member UUIDs joined — stable regardless of member order, which is what lets the orchestrator dedup.
- **`SyncOrchestrator.collectDuplicates`** runs off the **existing** proxy-filtered `workouts` fetch inside `process()` — no new HealthKit round-trips. Per-activity windows overlap, so the same pair can surface from several items; clusters are merged into `duplicateClusters` deduped by cluster id. `duplicateClusters` is ephemeral (reset each sync, like `items`), not persisted to the Recent-syncs log.
- **`HealthKitManager`** gained `sourceName(of:)` (→ `sourceRevision.source.name`, the name Tom sees in Health's source list) and `distanceMeters(of:)` (type-appropriate distance statistic, nil when absent). Read auth was added for `distanceWalkingRunning` + `distanceSwimming` so run/swim distance populates on the display — cycling read was already present from #37. This re-triggers the Health permission sheet once for those two types.
- **`ContentView`** shows a read-only orange "Possible duplicates" section under the sync results when `duplicateClusters` is non-empty: a per-cluster header (type + date) and one line per copy — `source · duration · distance` — with a hint to delete extras in the Health app.

## Why the #37 proxies don't false-positive

The distance-proxy workouts from #37 are 1-second cycling workouts near a ride's start. They're already excluded from the candidate pool in `process()` via `.filter { !isDistanceProxy($0) }` *before* `collectDuplicates` sees them, so they can't be flagged as duplicates of their own ride. (Even without the filter, the 1s vs full-ride duration gap would fail the ±60s duration test — but the filter is the real guard.)

## Testing

- **`DuplicateDetectionTests`** (10 cases): empty/singleton → no cluster; matching pair → one cluster of 2; different type / start-beyond-tolerance / duration-beyond-tolerance → no cluster; three-way cluster; differing distance still clusters (distance not a match key); two independent pairs → two clusters; stable cluster id regardless of input order.
- `HealthKitManagerTests.readSetContents` updated to assert the two new read types.
- The HealthKit-touching methods (`sourceName`, `distanceMeters`, `collectDuplicates`) follow the project's existing pattern of not being unit-tested directly — the pure clusterer carries the decision logic. Full XCTest pack green.

## Verification

Tom deployed to his phone and ran a sync — **no duplicates surfaced**, consistent with there simply being none in the recent window. The negative path (normal activities don't get flagged) is confirmed; the **positive path (a real duplicate actually gets clustered and displayed) was not exercised on-device**, because he has no current dupes to trigger it. Shipped on test-suite trust + the pure clusterer's coverage, with Tom watching for it to fire in normal use. Manual-verification boxes on the issue left for him.

## Decisions made and rejected alternatives

- **Read-only, no deletion.** Forced by #12; this is the "other app's duplicate" case #37 explicitly couldn't auto-clean.
- **Ride-along, not a wide historical scan.** Tom's call — cheapest, rides the existing fetch. Wide-scan left as a possible follow-up if outliers prove to live outside the recent window.
- **Distance shown, not matched on.** Keeps indoor-ride twins (no native distance) pairing correctly.
- **Ephemeral display, not logged.** Reviewed right after a sync, like `items`; no persistence added.
