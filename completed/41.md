# #41 — BG sync row counted skipped activities as synced; add tap-to-expand breakdown

**Closed:** 2026-06-02
**Branch:** `claude/busy-sammet-260dd8`

## What was wrong

Background-sync rows in **Recent syncs** showed "1 activity" even when nothing had actually been synced. This is the same overlap-noise class #32 fixed, just a different skip reason. Every BG fire re-fetches the last 24h of Strava activities (the #24 overlap). #32 stopped `.skippedAlreadyHasEffort` (the "already synced" re-fetch) from counting, but it *deliberately* left other skip kinds counting — `activitiesProcessed` excluded only `.skippedAlreadyHasEffort`, on the rationale that other skips are "signal."

In practice a recent activity that can *never* sync — most likely a walk with no `suffer_score` (Strava only assigns Relative Effort when it has heart-rate data), or an unmapped sport type — gets stamped `.skippedNoSufferScore` / `.skippedNoMatch` on every BG fire it falls inside the window for, and each one bumped the row count to "1 activity." Nothing was written; the activity was just looked at and skipped.

Compounding it, `SyncLogEntry` persisted only a *count*, never which activities or what happened to them — so there was no way to tap a row and see what the "1" actually was. Tom's feature ask (tap to expand) and the count confusion turned out to share one root change.

## What changed

- **`SyncLogEntry.items: [ItemSummary]`** — per-activity breakdown captured at log time. `ItemSummary` is a deliberately plain `Codable` struct (`id`, `name`, `startDate`, `outcome: String`, `wasWritten: Bool`), *decoupled* from the in-flight `SyncOrchestrator.ItemStatus` enum so renaming a status case can never break decoding of saved history. Backward-compatible: a hand-written `init(from:)` decodes `items` via `decodeIfPresent ?? []`, so entries logged before #41 (and the pre-#32 legacy shape) load cleanly.

- **`SyncOrchestrator.ItemStatus`** gained two computed props: `isWrite` (true only for the four write outcomes — `.written`, `.writtenWithDistance`, `.addedDistance`, `.writtenAsNew`) and `summaryLabel` (plain-text, color-free outcome string for the persisted summary). The live colored `statusLabel(for:)` in ContentView was left untouched (surgical — it works and carries per-case colors the log doesn't need).

- **Shared `buildLogEntry(at:source:)`** — both sync paths' `defer` blocks (`syncActivities` and `syncSingleActivity`) were near-identical and #41 grew the logic (build summaries on top of the existing count/error extraction). #32 had explicitly chosen not to extract "until a third call site appears"; the right trigger turned out to be the logic growing, not the call-site count. One helper now keeps the count + summary rules in one place.

- **Recent syncs headline = "N synced"** — derived from `items.filter(\.wasWritten).count`, not `activitiesProcessed`. A skip-only overlap re-fetch now reads "0 synced." Legacy rows (no persisted items) fall back to the old "N activities" label and stay non-tappable.

- **Tap-to-expand** — rows with item data get a chevron and a `withAnimation` toggle (expanded ids tracked in a `Set<UUID>`). Expanded shows each activity's name, date, and outcome — written items green, skips/errors grey. The existing ⚠ + red `firstItemError` caption row is unchanged.

## Decisions made and rejected alternatives

- **`ItemSummary` is plain strings + a Bool, not a `Codable` `ItemStatus`.** Making `ItemStatus` (which has associated `Double` values) directly `Codable` would couple the persisted log format to the compiler-synthesized enum encoding — brittle across case renames, exactly the failure mode the legacy-decode test guards against. A precomputed display string + `wasWritten` flag is stable and self-contained. Cost: the outcome words ("No match", etc.) now live in both `summaryLabel` and the live `statusLabel(for:)`. Accepted as the lesser evil vs. rewriting a working colored view.

- **Option A (count only writes), chosen over Option B (keep total, explain on tap).** Tom picked A: the headline number should match his mental model of "synced." Skips are demoted from the headline into the expansion. The "signal" #32 wanted from non-routine skips is preserved — it's one tap away, and errors still drive the ⚠ icon.

- **#32's tap-to-expand rejection reversed.** #32 called tap-to-expand "overkill for a debug surface that's expected to be empty most of the time." That held when the row only ever carried an error string; once Tom explicitly wanted the per-activity breakdown, the rationale no longer applied.

- **Kept `activitiesProcessed` on the entry.** Still computed and persisted unchanged — needed for legacy-row display and harmless to keep. Didn't rip it out; the headline just stopped reading from it for new rows.

- **Expansion colors only green/grey, no red for errors.** `ItemSummary` carries `wasWritten` but no `isError` flag, and the existing red `firstItemError` caption already surfaces the error text on the row. Adding a third state to the summary for a case already covered would be scope creep.

## What surfaced during verification

Tom built to his phone and confirmed it working — skip-only syncs read "0 synced" and tapping a row expands the breakdown. Shipped on that confirmation. Note carried into the session: the expansion only appears for syncs logged *after* this change; pre-existing history rows stay non-tappable (expected — no per-item data was persisted for them).
